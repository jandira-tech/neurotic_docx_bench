# Stage L1 — the cluster lens partition on jubarte-final-lossless

Executed 2026-08-04 against run `019fcc6f-4eb8-72f7-957e-799895a04342`
(`jubarte-final-lossless`, scorer `pagefair-v2`, corpus revision `b7f467074a51`).
Stage L1 of [jubarte-lossless-to-target.md](../jubarte-lossless-to-target.md),
S0.1 of [the execution contract](../jubarte-execution-contract.md).

Artefacts: [`results/l1_partition/jubarte-final-lossless.json`](../../results/l1_partition/jubarte-final-lossless.json)
and `.md`. Reproduce with `uv run python scripts/run_l1_partition.py`
(~52 s, regenerates all 166 candidates from scratch) and
`uv run python scripts/l1_markup_probe.py`.

**Summary for the impatient.** The gate fires `STOP_FIX_SCORER` at 76.5%, five
times its 15% threshold. **The gate's stated reason is not supported by the
evidence, and the programme should not stop to rewrite the scorer.** Plan 1's
hypothesis that lossless "renders the document faithfully and then *under-marks*
the edit" is **contradicted**: the candidates mark the same volume Word does
(median ratio exactly 1.000) and not one of the 124 emits no markup. The real
defect is neither under-marking nor a broken scorer — it is that lossless emits
**paragraph-granular replacement where Word emits an in-place intra-paragraph
edit**. That is engine work, it is not in Stage L2's sub-work table, and it is
what L2 should be built around.

---

## 1. The obstacle, and why the recorded data could not answer this

`results/bench.jsonl` records only run-level lens counts. The per-document
verdicts do survive, in
`results/detail/019fcc6f-…__script_redlines__excluded.json.gz` — but only for
**46 of the 166** cluster documents.

The reason is a real defect in the bench, not disk pressure.
`cli._functional_stage` resolves its source DOCX through `cli._source_docx_map`
(cli.py:104), which globs mapping CSVs and `docx_source` dirs under
**`cfg.source_of_truth.parent` only** — i.e. `corpus/word_based`. `bench.yaml`
declares three corpus pools; the third, `corpus/word_redlines_superdoc`
(400 pairs), is invisible to it. So:

| | resolvable | of the 166-doc cluster |
|---|---:|---:|
| `word_based` + `word_based_randomized` (what the run lensed) | 403 | **46** |
| all three declared pools | 803 | **166** |

The 46 recorded verdicts are exactly the `word_based`-only subset — verified,
not assumed. Partitioning on them would have been a partition of a **biased 27%
subsample drawn from one corpus**, and it gives a materially different answer
(64.4% BOTH_HOLD on 45 judged, versus 76.5% on 162). So the candidates were
regenerated and the lens re-run over the whole cluster.

> **Reportable in its own right.** The published `n_functional_checked` = 377
> and `lens_disagree_rate` for this run are computed on 377 of 763 documents,
> and the 386 missing ones are missing *by corpus pool*, not at random. Every
> lens-derived figure for every run using this config carries the same
> single-pool restriction. This is the D1 disease — figures with different `n`
> presented as the same measurement — in the lens layer.

3. **Verdict agreement.** On the 46 documents the original run *did* lens, the

## 4. The gate fires. Its stated reason does not survive contact with the documents.

`cluster_lens.Bucket.BOTH_HOLD` is documented as *"Markup correct, the SCORER
disagrees — a benchmark defect."* That is an **inference**, and the instrument
does not license it.

`functional_lens` compares **text**: it accepts and rejects the candidate with
the bench's neutral machinery and compares extracted body text against next and
base. Everything that decides how a redline *renders* is outside that
comparison — which paragraph a change sits in, whether an edit is marked
in-place or as a delete-plus-insert of a whole paragraph, and formatting-change
markup (`w:rPrChange` / `w:pPrChange`). A candidate can satisfy both invariants
and still be a visibly different redline from Word's.

So I compared each BOTH_HOLD candidate against **Word's own oracle redline
DOCX** for the same pair (`scripts/l1_markup_probe.py`):

**Volume — is lossless under-marking?** No.

| | result |
|---|---|
| inserted chars, candidate/oracle | median **1.000** (n=117) |
| deleted chars, candidate/oracle | median **1.000** (n=122) |
| within 0.8–1.25× of the oracle on both | **101/124** |
| candidates emitting no markup at all | **0/124** |

**Shape — is it the same redline?** No.

| | result |
|---|---|
| paragraphs carrying both a `w:ins` and a `w:del` (the Word-style in-place edit) | candidate median **0**, oracle median **1** |
| candidate has fewer in-place paragraphs than the oracle | **81/124** |
| candidate has **none** where the oracle has some | **69/124** |
| candidate has more paragraphs than the oracle | **64/124** |

That is the defect, stated plainly: **lossless deletes a whole paragraph and
inserts a whole replacement paragraph where Word marks the change inside one
paragraph.** The accept/reject invariants cannot see it, because both
arrangements accept and reject to the same text.

### Two documents, rendered

**`super_editor__custom_list_numbering1_7eb9fda4_super_editor__custom_list1_77f82bd7`**
(score 51.41, `ink_f1` 0.138, `ssim_full` 0.974). The tracked changes are
substantively the same edit:

```
candidate  ins: ['Num 1', 'Num 1.1', 'Num 1.2', 'Num 1.2.1', 'Num 1.3']   (5 frags,  35 chars)
oracle     ins: ['Num', 'Num 1.1', 'Num 1.', 'Num 1.2.1', 'Num 1.3']      (5 frags,  32 chars)
candidate  del: ['  “SECTION 1”', 'a  ', 'b', 'c', '”Section 2”', 'a', 'b'](7 frags,  31 chars)
oracle     del: ['  “SECTION', '”', 'a  ', 'b', 'c', '”Section ', '”', 'a', 'b'] (9 frags, 28 chars)
```

Rendered, they are not the same page. The candidate shows the inserted list as
its own five-line block, then the struck `SECTION 1 … SECTION 2` block below it.
Word interleaves them: `1. Num ~~"SECTION 1"~~` on one line, with old list
numbers shown in brackets (`[1.2.]`, `1.1.[1.2.1.]`) beside the new ones.

**`font_size_demo_id_paraid_overflow_footnotes_sample`** (score 50.49,
`ink_f1` 0.171, `ssim_full` 0.989). The candidate puts the inserted `Ouch¹,²` on
its own line and strikes `Font Size Demo` on the next. Word puts both on **one**
line: `Ouch¹,²~~Font Size Demo~~`. Everything below shifts by a line. Separately,
the candidate marks footnote 2 (`Fin.`) as changed; Word leaves it unmarked —
so here lossless marks *more* than Word, not less.

### Why that costs ~50 points

Per-page medians for the BOTH_HOLD set against the ≥90-scoring reference group:

| metric | BOTH_HOLD (263 pages) | ≥90 reference (726 pages) | weight |
|---|---:|---:|---:|
| `ssim_full` | 0.904 | 1.000 | 0.25 |
| `ssim_small` | 0.832 | 1.000 | 0.15 |
| `ink_f1` | **0.326** | 1.000 | 0.20 |
| `edge_iou` | **0.188** | 1.000 | 0.15 |
| `color_sim` | **0.000** | 1.000 | 0.15 |
| `delta_e` | 31.0 | 0.0 | — |
| `blob_penalty` | 0.078 | 0.008 | 0.10 |

Recomputing the six weighted terms per page reproduces the recorded page score
**exactly** (median 51.61 both ways, max absolute deviation 0.0000 over 263
pages), so the score is fully accounted for by this table and nothing else is
acting on it. The page itself is largely right — `ssim` stays high, which is the
page-fidelity strength the plan correctly identified — and the three
**position-sensitive** terms collapse together.

`color_sim` is saturated, not merely low. `score.py:292` computes
`max(0, 1 − min(ΔE / color_deltaE_max, 1))`, and the observed ΔE of 31.0 exceeds
the configured maximum of 20.0, so the term clamps to exactly 0.0 and forfeits
its full 0.15 weight. It is not a separate colour defect — comparing colours at
displaced ink positions is what produces the large ΔE in the first place.

## 5. Is the scorer blameless? Not entirely — but not in the way the gate says.

One underlying defect (displaced redline ink) drives `ink_f1`, `edge_iou` and
`color_sim` down simultaneously. Those carry **0.50 of the six-term weight
between them**, so a single positional cause is charged three times, and
`color_sim` additionally saturates to zero rather than degrading smoothly.

That is a legitimate criticism of the scorer's construction and worth a bounded
investigation. It is **not** the finding the L1 gate claims. The gate claims the
markup is correct and the scorer is under-crediting it; what is true is that the
markup is *functionally valid but structurally different from Word's*, the
scorer is right to penalise it, and it plausibly over-penalises by
triple-counting. Nothing here invalidates published scores, and I would not
report it as a benchmark defect that requires halting.

## 6. The other buckets — L2's table is wrong here too

For `ACCEPT_ONLY` (n=29), Stage L2's table says *"insertions marked; deletions
dropped rather than struck"* and routes the work to the **deletion path**. That
predicts `reject(candidate)` would come out **shorter** than base. Measured
(normalised character length, a proxy — directional, not exact):

| | shorter (content dropped) | longer (content retained) | same/error |
|---|---:|---:|---:|
| `ACCEPT_ONLY` — reject vs base | 10 | **17** | 2 |
| `REJECT_ONLY` — accept vs next | 1 | 2 | 0 |
| `NEITHER` — accept vs next | 1 | 5 | 0 |

The dominant mode is the **opposite** of the table's: rejection *retains* content
that base does not have, i.e. insertions emitted **untracked** so `reject` cannot
strip them. That is the insertion path, not the deletion path, for roughly
17 of 29.

## 7. Cross-tabulation

BOTH_HOLD is concentrated in structural-content families — `list` 26 docs (93%
of that token's judged documents), `table` 22 (76%), `math` 19 (95%), `ooxml` 15
(88%), `combos` 12 (92%). Exactly the families where a change spans structured
paragraphs and where paragraph-granular replacement is most visible. ACCEPT_ONLY
leans on `styles` 6 (75%), `localized` 5 (100%), `hyperlink` 4 (80%), `heading`
5 (62%) — a different, style-resolution-flavoured population, and the same
family Stage L3 targets. `REJECT_ONLY` (3) and `NEITHER` (6) are too small for
any token to clear the minimum population; nothing should be inferred from them.

## 8. What I recommend

1. **Do not stop to fix the scorer.** The gate's threshold is exceeded five
   times over, but on a reason the evidence contradicts. Publishing "our
   benchmark under-credits correct markup" on this basis would be the D3 disease
   with the sign flipped — our own instrument reporting a defect that is not
   there.
2. **Do not run Stage L2 as written.** It routes 76.5% of the cluster to "not
   engine work — escalate", and mis-routes ~59% of `ACCEPT_ONLY` to the deletion
   path. Both are wrong.
3. **Build L2 around the mechanism this stage actually found:** emit in-place
   intra-paragraph revisions instead of paragraph-granular replace. Sized by the
   probe, it is the dominant defect in 69–81 of 124 BOTH_HOLD documents, and
   BOTH_HOLD is 76.5% of the cluster. It is a new row for L2's sub-work table.
4. **Tighten the L1 gate before it is used again.** `BOTH_HOLD` must be renamed
   and re-documented to what it establishes — a *functionally valid* redline —
   and the gate must not fire `STOP_FIX_SCORER` on a text-only invariant. The
   cheapest structural invariant that would have caught this: compare the
   candidate's in-place-revision paragraph count against the oracle's, which is
   already implemented in `scripts/l1_markup_probe.py`.
5. **Fix `cli._source_docx_map`** to resolve across every declared corpus pool.
   Until then every lens figure the bench publishes is a single-pool subsample.
6. **File the 3 `accept_changes` table crashes** (`no 'tc' element at
   grid_offset=…`) as a bench bug.

## 9. Honest limits

- The lens verdicts are trustworthy (46/46 control). The **claim about *why* the
  cluster scores ~51** rests on the markup probe over 124 documents plus two
  rendered exemplars. The probe's two axes (volume, in-place paragraph count)
  are proxies, not a proof of visual cause; I did not render all 124.
- The `shorter/longer` split in §6 is a character-length proxy and should be
  read as direction, not magnitude.
- I did not verify that regenerated bytes equal the scored bytes; the run
  directory was deleted. The 46/46 verdict agreement plus the identical engine
  hash is the strongest available substitute, and it is weaker than a byte
  comparison.
- 19 of 124 BOTH_HOLD documents carry a `page_count_mismatch` (against 1 of 277
  in the ≥90 group). Those have a pagination defect on top of the alignment one
  and may not be fixed by the L2 mechanism above.
- **What would falsify this:** if fixing paragraph alignment on a handful of
  named BOTH_HOLD documents does not move their scores materially, the
  mechanism is wrong and §5's triple-counting criticism becomes the leading
  explanation instead. That is a cheap experiment and it should be run before
  L2 is sized.

## 10. Contract note

C5 excluded blind pairs from the gate's denominator specifically to prevent a
false `STOP_FIX_SCORER`, and reasoned that this was "the D3 disease in
miniature". The reasoning was right and the fix was correct — and a false STOP
arrived anyway, through a door C5 did not cover: **text-level equivalence is not
markup correctness.** The blind-pair exclusion removed one instance of the
problem; the inference attached to `BOTH_HOLD` is the same problem one level up.
Worth recording, because it says the gate needs a structural invariant, not a
better denominator.
