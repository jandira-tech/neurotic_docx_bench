Approved by Arthur on 2026-09-27 (answers to the numbered assessment): 1a, 2a plus a
release script, 3a, 4b, 5b, 7a, 8a with two dataset repos and `upload_large_folder`,
9 all three (cache, profile, torch backend), 10 bun test working in the Linux VM,
11a, 12a.

Purpose stays what it was: the score exists to improve jubarte. Every command below
must let a jubarte developer score an unpublished build on a handful of documents in
one line.

## Decisions (restated as they will be built)

1. Frozen results pages are named by bench version: `RESULTS_v0.6.0.md` is written the
   moment `bench_version` changes, with a header stating docset ids, scorer version,
   renderer ids and freeze date. A running integer is not used.
2. Word is the headline renderer. The headline group is the newest eligible group whose
   `renderer_id` starts with `word-`; `renderer_id` carries the Word version. soffice
   groups are history. CI on PR and push runs the Python tests, `bun test` and
   `bench report --check`; no LibreOffice, no bench runs, no commits from CI. A manual
   `workflow_dispatch` soffice smoke on the gate set stays and uploads an artifact only.
   Releases go through `scripts/release.py`: it refuses unless Word is reachable on the
   machine, the store's headline groups were rendered with that Word version, and the
   results pages are current (`bench report --check`). It then tags, builds, publishes to
   PyPI and creates the GitHub release. Any failed check exits non-zero before anything
   is published.
3. One scoring pass per candidate: render once, rasterize once, compute pagefair-v2
   (headline, unchanged), text-boundary jaccard (docxide's metric, reimplemented in
   Python with a parity test against recorded Rust outputs) and the scoreboard contract
   checks, all as columns on the same row. docxide's own SSIM is dropped (pagefair-v2
   carries SSIM at 40%). The vendored Rust scorer is retired.
4. Gate: a tool enters the main page only when, on the gate set (50 documents per
   family, stratified deterministic sample, own docset id, subset of the full docset),
   its ITT median beats the null-baseline calibration row by 10 points and its 95%
   bootstrap CI excludes the null-baseline median. Below-gate tools are listed in
   RESULTS_DETAILED.md under "Below the gate" with their gate score.
5. Families in 0.7.0: `redline`, `accept`, `render` (converters and editors, with an
   input-kind column: plain, redline, accepted). `roundtrip` stays as a detailed-only
   table. Legacy family names map onto the new ones for history.
6. Legacy archive as built.
7. grok_run imports: `fixtures_500` and the part a/b originals with their Word PDFs
   (part_a run2 and part_b run2 and part_b original) to `render`; the A-vs-B compares and
   the 500 extra redlines (docx plus Word PDF oracles, `wordpdf_redline_oracles`) to
   `redline`. Provenance from MANIFEST.json and 500_en_sources.jsonl, ODC-By-1.0
   attribution, sha256 manifest, docset ids.
8. Versioning: 0.6.0 = base commit 962fb8e0 plus packaging metadata only (version, wheel
   excludes `utils/`, competitors in a `competitors` extra), tagged `v0.6.0`. 0.7.0 = the
   merged stack. Every store line stamps `bench_version`; major.minor joins the
   comparability group key. Hugging Face: two dataset repos, `arthrod/neurotic_docx_bench`
   for results plus the fixtures each run used, and `arthrod/neurotic_docx_bench-fixtures`
   for the source fixtures; uploads use `huggingface_hub.upload_large_folder`;
   `bench fixtures download [--revision]` verifies the sha256 manifest;
   `bench results upload [--with-outputs] [--prune-local]` (prune only after checksum
   verification, off by default).
9. Scoring cost: (a) content-addressed render/raster/score cache keyed by candidate
   sha256, oracle sha256, scorer version, dpi, renderer id; (b) `bench profile` reporting
   per-stage timings on a sample; (c) torch backend behind `--device auto|cpu|mps|cuda`
   for the dominant kernels with a parity test against the skimage path and CPU
   fallback.
10. `bun test` replaces vitest; the 12 test files move to `bun:test`; coverage via
    `bun test --coverage`; verified in the Linux VM with a linux `node_modules`.
11. Word control document: one canary document stays open for the whole session; its
    phrase must never appear in any output; its paragraph count is re-checked after every
    item; it is the only document exempt from `close every document saving no`.
    `--allow-open-docs` is removed; preflight refuses to start with foreign documents
    open; README states the operator must not use Word during a run.
12. `bench score --benchmark redline|accept|render --oracle DIR (--files a,b,c | --dir D)
    [--renderer word|soffice] [--json OUT] [--record --tool ID]`: `--files` are candidate
    outputs already produced (score only). Stem matching against the oracle directory;
    unmatched names reported with the closest stem; nothing written under `results/`
    unless `--record`, which appends to `results/dev.jsonl` with `published: false`, a
    file the report never reads. `bench run --unpublished` does the same for whole runs.

## Deviations recorded while building

- Item 8, `upload_large_folder`: huggingface_hub 2.0.0 (released 2026-09-24, the version
  the lock resolves) removed `upload_large_folder`; its migration guide says to use
  `upload_folder`. `hub.py` uses `upload_folder` and verifies every uploaded file against
  the repo tree (LFS sha256, or git blob sha1 for small files) after the upload.
  `pyproject.toml` pins `huggingface-hub>=2.0`.
- Item 1, first freeze: `RESULTS_v0.6.0.md` is the page published at tag `v0.6.0`
  (checked out and frozen by `bench report`), not the ledger-rebuilt page that was on
  disk when the version moved. Its metadata header is derived from the stores because
  that page predates the provenance line.
- Item 2, Word-rendered: `oracle:microsoft_word` counts as a Word renderer alongside
  `word-<version>`, so the converter benchmarks (scored against Word's own export)
  keep their main-page tables. Gate-set groups are left out of `history_groups` (they
  are the gate, not a comparability group), and the calibration tool's rows are not
  listed among the excluded rows of a benchmark with no eligible row.
- Item 4, scope of the gate: the gate applies to the six `bench run` benchmarks
  (`policy.GATED_BENCHMARKS`), the ones `bench docset` records a gate set for and that
  have a null-baseline run. The converter benchmarks have neither and are not gated.
  Roundtrip is gated for now; item 5 (detailed-only) decides whether it stays so.
- Item 4, `bench run --gate-set`: named `--gate-set` because `--gate/--no-gate` is the
  snapshot regression gate. It filters the run's source to the gate documents of the
  source-keyed benchmarks (script_redlines, accepted_changes, visual_*); the roundtrip
  stage draws on the fixed roundtrip corpus and keeps its full docset on a gate-set run.
- Item 4, consequence on the pages: until Word-rendered full and gate-set runs exist,
  the six benchmark tables read "No eligible rows" with every tool listed under "Not
  ranked" (reason: renderer legacy-soffice is not Word). The LibreOffice rows stay in
  History.
- Pre-existing, not touched here: `tests/test_cli_driver.py::test_generate_then_render`
  asserts a LibreOffice render of a Word redline DOCX scores 100 against the Word oracle
  PDF; it fails on the base commit in the Linux VM too (98.86).
- Item 3, parity engine: the frozen `tests/reference/docxide_page_metrics.json` was recorded
  by upstream's `page-metrics` binary over mutool 1.28.4; the Python port drives MuPDF
  through PyMuPDF 1.28.0, which bundles MuPDF 1.29.0. Four of five pairs match to 1e-12;
  on `file_100_file_101_redline` MuPDF 1.29 splits one equation line on the LibreOffice
  render's page 6 that 1.28.4 keeps whole, moving text_boundary from 95/190 (0.5) to
  105/191. The ported algorithm run over mutool 1.28.4 output reproduces 0.5 exactly, so
  the value was re-frozen and the reference now carries an `_engine` block; the parity
  test refuses to run on a different MuPDF build rather than tolerate drift.
- Item 3, columns: the same-row columns are `ink_jaccard`, `text_boundary`,
  `max_break_drift` on every `score_pdf_pair` result, computed from the pass's own rasters
  at the pass DPI (144 for the benchmarks); the `docxide_metrics` converter track keeps
  upstream's 150 DPI so its numbers stay comparable with docxide-pdf's own. "Scoreboard
  contract checks" on the row are the functional accept/reject lens columns that the CLI
  already merges (`functional_accept_ok` and friends), unchanged.
- Item 3, Rust sources: `src/neurotic_docx_bench/utils/docxide-metrics/` is untracked
  (`git rm --cached`), not deleted from disk; the directory is removed by hand.
- Item 9a, key: "scorer version" is not a hand-maintained number but a fingerprint over
  the scoring sources (`score.py`, `score_v2.py`, `page_metrics.py`, `pipeline.py`,
  `raster.py`), the MuPDF build and a cache schema constant, so a scorer edit or a PyMuPDF
  upgrade invalidates score entries without anyone remembering to bump anything. The base
  PDF's sha256 joins the key when a base PDF is scored (it changes the null/skill columns).
- Item 9a, location: the cache lives in `.bench-cache/` next to the results directory
  (git-ignored), overridable with `BENCH_CACHE_DIR`, disabled with `BENCH_NO_CACHE=1` or
  `bench run --no-cache`; `bench cache [--clear]` inspects it.
- Item 9a, timings: a row restored from the cache is marked `cached: true` and carries no
  `raster_ns`/`score_ns`; a restored render is `cached: true` with `duration_ns=None`.
  Per-run speed numbers (`render_s`, `raster_s`, `score_s`, `overall_*_speed`) therefore
  cover only fresh work; speed measurements use `--no-cache`. Page rasters are still
  written under the run's work dir on a hit so galleries and diagnostics are unchanged.
- Item 9a, scope: `bench run` (render, accept-compare and roundtrip stages) is cached;
  `bench compare` is not. Cached one-off scoring arrives with `bench score` (item 12).
- Item 9a, lifetime: the cache is configured by `bench run` for the duration of that
  command only (`try`/`finally` around the drive) so a later command in the same process,
  or a later test, never inherits it.
- Item 9b, shape: `bench profile` reuses the per-document stage timings `bench run`
  already collects (`generate_s`, `render_s`, `raster_s`, `score_s`) rather than adding a
  second instrumentation layer; the driver hands them back through a `timings_sink`, and
  the command is the normal pipeline with emit, gate, tool updates and the content cache
  all off. The sample is `--sample N --seed S` over the sorted file list (`--limit` keeps
  taking the first N), so a profile is repeatable and two profiles compare the same
  documents.
- Item 9b, roundtrip: the roundtrip stage draws its sample from `out/roundtrip/<tool>/`
  with the same seed; `bench profile --roundtrip` still renders the roundtrip oracle through
  soffice before timing (that oracle render is not part of the profile).
- Items 2 and 4, test fallout found on this branch: the synthetic rows in
  `tests/test_compact_results.py` had no Word renderer and no gate set, so the headline
  table they expected read "No eligible rows" after the policy change. The rows now
  carry `renderer_id: word-16.0`, docset ids and a gate-set null-baseline run, and the
  byte-identity test asserts the tools are ranked.
- Item 8, test fallout found on this branch: `superdoc-sdk` moved to the `competitors`
  extra, so `tests/test_superdoc_pins.py` no longer found it among `dependencies`; the
  pin test reads both lists.
- Pre-existing in the Linux VM at the base commit, not touched here:
  `tests/test_diagnostics_ratchet.py` (3, the run id is not in `results/bench.jsonl`),
  `tests/test_word_pdf.py` (2), `tests/test_superdoc_pins.py::
  test_pin_documentation_comment_matches_the_actual_pins` (the `bench.yaml` header lacks
  `superdoc@2.18.0`), `tests/test_render_playwright.py` (5, no Chromium under
  `~/.cache/ms-playwright`) and `test_generate_then_render` (above).
